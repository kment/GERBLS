Full usage
==========

.. attention:: Make sure you have read :doc:`getting_started` (specifically :ref:`things-to-know-label`).

Specifying the input data
-------------------------
In order to run GERBLS, the light curve has to be stored in a :class:`gerbls.pyDataContainer` object. **The data must be time-sorted before storing it.** Given input data arrays ``time``, ``flux``, and ``err`` (flux uncertainties), they can be copied into a :class:`gerbls.pyDataContainer` object by running:

>>> data = gerbls.pyDataContainer()
>>> data.store(time, flux, err)

Alternatively, :meth:`gerbls.pyDataContainer.assign` avoids making a copy of the data, but can lead to crashes if any of the underlying arrays get deallocated.

Specifying searched transit durations
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
There are three different ways (``duration_mode`` values) that the searched transit durations can be specified, which affect the numerical values specified by ``durations``, ``min_duration_factor``, and ``max_duration_factor``:

* 'constant' - numerical values represent actual search durations in units of time (this is the way :external:class:`astropy.timeseries.BoxLeastSquares` implements durations).
* 'fractional' - numerical values represent `duty cycles` (durations in phase) and are multiplied by the trial period(s) being searched. Thus, duration values in time scale with :math:`P` (orbital period).
* 'physical' - numerical values represent fractional multipliers compared to the expected transit duration for a circular orbit at the searched period(s). Thus, duration values in time scale with :math:`P^{1/3}`. This option requires the mass and radius of the host star to be set via ``target`` in order to estimate transit durations.

The numerical values can then either be specified directly via ``durations`` (recommended) or as a range via ``min_duration_factor`` and ``max_duration_factor``. In the latter case, the range of test durations will be sampled with a time resolution equal to ``t_samp``. If ``duration_mode == 'fractional'``, all numerical values should be strictly between 0 and 1 (fractions of the trial period). If ``duration_mode == 'physical'`` is used, it may be worth testing numerical values greater than 1 (i.e. transits longer than the expected duration for a circular orbit) to account for eccentric orbits or uncertainties in the stellar mass and radius.

(Optional) Automatic downsampling
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The expected transit duration for a planet on a Keplerian orbit around a given star scales with :math:`P^{1/3}`. This leads to a several issues in typical brute-force BLS setups that run on light curves with constant time sampling: 

* A shorter data cadence is necessary when searching short orbital periods so that the (comparatively short) transits are not missed, but it makes the search inefficient at longer periods where each transit is expected to contain more in-transit data points. This makes the BLS slower than it needs to be.
* Constant time sampling can also induce a period-dependent bias in the BLS sensitivity, because longer periods are tested at a higher phase resolution. This can cause spurious dips in the light curve to appear more prominent at longer periods.

To account for this, GERBLS implements a ``downsample`` option to automatically downsample the data to a longer cadence when searching longer orbital periods. Consequently, the average number of in-transit data points expected for a Keplerian orbit is kept roughly constant as a function of search period (with the default value of ``downsample_invpower = 3``). Downsampling is triggered each time the value of :math:`P^{1/3}` (the transit duration scaling) grows by a factor of ``downsample_threshold``, by default 1.1. Larger values increase precision at the cost of more computational time spent on downsampling; in general, the downsampling should only require a fraction of the BLS runtime. **Although not turned on by default, experimenting with** ``downsample = True`` **is highly recommended.**

.. tip:: Turning on automatic downsampling makes GERBLS naturally produce a period spacing that is close to statistically optimal, as shown in :ref:`period-grid-label`. It also reduces BLS runtimes: see :doc:`benchmarks` for more info.

Running the BLS
---------------

After setup, the BLS spectrum can be generated with the following method:

    .. automethod:: gerbls.pyFastBLS.run

The ``verbose`` option will print some limited output, such as the total runtime and the number of periods searched.

Retrieving and analyzing the results
------------------------------------

After running the BLS, the results can be retrieved by passing the :class:`gerbls.pyFastBLS` object (``bls`` in the example below) to :class:`gerbls.pyBLSAnalyzer`:

>>> results = gerbls.pyBLSAnalyzer(bls)

Its various properties can then be accessed to obtain best-fit box model parameter values at each tested orbital period:

================= ===================================================
Property          Description
================= ===================================================
``results.P``     list of tested periods
``results.dchi2`` BLS statistic (:math:`\Delta\chi^2`) at each period
``results.t0``    best-fit transit mid-point at each period
``results.dur``   best-fit duration at each period
``results.mag0``  best-fit flux baseline at each period
``results.dmag``  best-fit transit depth at each period
``results.snr``   estimated SNR at each period
================= ===================================================

In addition, the Signal Detection Efficiency (SDE) can be calculated at each tested period via :meth:`gerbls.pyBLSAnalyzer.get_SDE`. We top peaks in the BLS spectrum can be identified via :meth:`gerbls.pyBLSAnalyzer.generate_models`, which returns a list of :class:`gerbls.pyBLSResult` objects:

    .. automethod:: gerbls.pyBLSAnalyzer.generate_models
        :no-index:

We recommend setting ``use_SDE = True`` to identify peaks in the SDE spectrum rather than the :math:`\Delta\chi^2` spectrum, as this is more robust against period-dependent biases. See the example below for further details.
